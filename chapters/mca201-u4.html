MCA 201 · Unit IV

Transactions, Concurrency, Recovery & Distributed Databases

Overview

This unit explains how a DBMS keeps data correct when many users work at once and when systems crash. It covers transactions and ACID, concurrency control, deadlock, log-based recovery, and a short introduction to distributed databases.

Detailed notes

1. Transaction and ACID properties

A transaction is a sequence of operations that forms one logical unit of work (e.g. transferring money). Properties:

  • Atomicity – all or nothing (ensured by the recovery manager).
  • Consistency – moves the database from one valid state to another (programmer/integrity constraints).
  • Isolation – concurrent transactions do not interfere (concurrency-control manager).
  • Durability – committed changes survive failures (recovery manager).

2. Transaction states

Active → Partially committed (after last statement) → Committed; from Active or Partially committed a failure leads to Failed → Aborted (rolled back; may restart or kill the transaction).

3. Atomicity and durability implementation

Using the shadow-copy scheme (a db-pointer switches to the new copy on commit) or, more commonly, the log (write-ahead logging).

4. Concurrent executions and serializability

Concurrency improves throughput and response time but can cause lost update, dirty read, unrepeatable read and phantom problems. A schedule is serializable if it is equivalent to some serial schedule. Conflict serializability is tested with a precedence graph: the schedule is conflict serializable iff the graph has no cycle. Conflicts occur when two transactions access the same item and at least one writes.

5. Concurrency control

  • Lock-based: shared (S) lock for reading, exclusive (X) lock for writing. Two-phase locking (2PL) has a growing phase (acquire locks) and a shrinking phase (release only); it guarantees serializability.
  • Timestamp-based: older transaction gets priority using read/write timestamps.
  • Optimistic (validation) and multiversion methods are also used.

6. Deadlock

Deadlock occurs when each transaction in a set waits for a lock held by another in the set. Four conditions: mutual exclusion, hold and wait, no pre-emption, circular wait. Prevention: wait-die and wound-wait schemes, lock-all-at-once. Detection: cycle in the wait-for graph, then abort a victim. Recovery: rollback of the victim.

7. Failure classification, storage types and stable storage

Failures: transaction failure (logical error, system error), system crash (power loss, memory lost) and disk failure. Storage: volatile (RAM), non-volatile (disk, tape) and stable storage (information is never lost; simulated by keeping multiple copies on separate disks with careful write protocols). Data access happens by transferring blocks between disk and main-memory buffers (input(B), output(B), read(X), write(X)).

8. Log-based recovery

The log is a sequence of records: <T start>, <T, X, old, new>, <T commit>, <T abort>. The write-ahead rule: the log record must reach stable storage before the data it describes.

SchemeWrites to DBRecovery
Deferred modificationOnly after the transaction commitsOnly REDO committed transactions; uncommitted ones are ignored (no old value needed)
Immediate modificationCan happen before commitUNDO uncommitted, REDO committed transactions

9. Checkpoints

Periodically the system writes all log records and modified buffers to disk and adds a <checkpoint> record. Recovery then needs to examine only transactions that were active at or started after the last checkpoint, saving time.

10. Distributed databases

A distributed database stores data on multiple sites connected by a network, appearing as one database to users. Advantages: local autonomy, availability, performance, modular growth; drawbacks: complexity, cost, harder concurrency control and recovery.

  • Replication: copies of a relation at several sites (better availability and read speed, costly updates). Full or partial replication.
  • Fragmentation: Horizontal (subset of rows, by selection), Vertical (subset of columns, each fragment keeps the primary key) and Mixed (both). Fragments must be lossless: rebuilt by union (horizontal) or join (vertical).

Important questions

Q1. Explain ACID properties with an example.

Atomicity, Consistency, Isolation, Durability, illustrated by a fund transfer where both debit and credit happen or neither does.

Q2. Draw and explain the transaction state diagram.

Active, partially committed, committed, failed, aborted, with transitions as described in the notes.

Q3. What is serializability? How is it tested?

Equivalence to a serial schedule; conflict serializability is tested by a cycle-free precedence graph.

Q4. What is deadlock? How can it be prevented or detected?

Circular wait among transactions; prevention by wait-die/wound-wait, detection by cycle in the wait-for graph.

Q5. Compare deferred and immediate database modification.

Deferred writes after commit (redo only); immediate may write before commit (undo and redo needed).

Q6. Explain horizontal and vertical fragmentation.

Horizontal splits rows by condition; vertical splits columns with key repeated; reconstruct by union and join respectively.

Quick revision

  • ACID = Atomicity, Consistency, Isolation, Durability.
  • States: Active → Partially committed → Committed / Failed → Aborted.
  • Serializable ⇔ precedence graph has no cycle.
  • 2PL = growing + shrinking phase.
  • Deadlock = cycle in wait-for graph; victim rollback.
  • Deferred = REDO; Immediate = UNDO + REDO; checkpoint limits recovery work.
  • Fragmentation: horizontal, vertical, mixed; replication = copies.

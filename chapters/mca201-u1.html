Introduction & ER Model

Overview

This unit lays the foundation of the whole subject. It explains why we use a Database Management System (DBMS) instead of plain files, how a DBMS hides complexity from users, and how a real-world problem is modelled on paper using the Entity-Relationship (ER) model before being converted into tables. ER diagrams and ER-to-table conversion are asked almost every year.

Detailed notes

1. Advantages of the DBMS approach

A DBMS is software that creates, stores, retrieves and controls access to an organised collection of related data. Compared with a file-processing system it gives:

  • Reduced redundancy and inconsistency – one copy of data instead of many.
  • Data sharing and concurrent access by many users.
  • Integrity constraints – rules such as “age > 0” enforced centrally.
  • Security – user-wise authorisation.
  • Backup and recovery after failures.
  • Data independence – programs are not affected by storage changes.

2. Views of data (three-level architecture)

LevelDescribesSeen by
Physical (internal)How data is actually stored (files, indexes, blocks)DBA, system programmers
Logical (conceptual)What data is stored and the relationships among themDBA, designers
View (external)Part of the database relevant to one user groupEnd users, application programmers

3. Data independence

  • Physical data independence – change the internal schema (e.g. add an index) without changing the logical schema.
  • Logical data independence – change the logical schema (e.g. add a column) without changing external views or programs. It is harder to achieve.

4. Schema and subschema

The schema is the overall design (structure) of the database and changes rarely. A subschema is the part of the schema used by one application or user (an external view). The data stored at a given moment is called an instance.

5. Data models

A data model is a collection of concepts for describing data, relationships, semantics and constraints. Main types: hierarchical (tree), network (graph), relational (tables), ER (conceptual) and object-oriented.

6. Database languages

  • DDL (Data Definition Language) – CREATE, ALTER, DROP. Output is stored in the data dictionary.
  • DML (Data Manipulation Language) – SELECT, INSERT, UPDATE, DELETE. Can be procedural or declarative (non-procedural, e.g. SQL).
  • DCL – GRANT, REVOKE. TCL – COMMIT, ROLLBACK, SAVEPOINT.

7. Transaction management, DBA and users

A transaction is a logical unit of work that must be executed completely or not at all (ACID). The Database Administrator (DBA) defines schema, grants access, tunes performance and manages backup/recovery. Users: naive users, application programmers, sophisticated users (analysts) and specialised users.

8. Data dictionary and system architecture

The data dictionary is a repository of metadata (data about data): table names, column types, constraints, users and privileges. The DBMS has two main parts: the query processor (DDL interpreter, DML compiler, query evaluation engine) and the storage manager (authorisation manager, transaction manager, file manager, buffer manager).

9. ER model: basic concepts

  • Entity – a distinguishable real-world object; entity set – collection of similar entities.
  • Attribute types: simple/composite, single-valued/multivalued, derived, and null-able.
  • Relationship – association among entities; its degree is the number of participating entity sets (unary, binary, ternary).

10. Mapping constraints

Cardinality: one-to-one, one-to-many, many-to-one, many-to-many. Participation: total (every entity must take part) or partial.

11. Keys

Super key – any set of attributes that uniquely identifies a row. Candidate key – minimal super key. Primary key – the chosen candidate key. Foreign key – attribute referring to the primary key of another table.

12. Weak and strong entity sets

A strong entity set has its own primary key. A weak entity set has no primary key of its own; it depends on an owner (identifying) entity and is identified by the owner’s key plus its own discriminator (partial key). Drawn with a double rectangle; the identifying relationship uses a double diamond.

13. Specialization, generalization, aggregation, inheritance

  • Specialization – top-down: split an entity set into sub-groups (Employee → Manager, Clerk).
  • Generalization – bottom-up: combine similar entity sets into a higher-level one.
  • Inheritance – lower-level entities inherit attributes and relationships of higher-level ones (“ISA” relationship).
  • Aggregation – treats a relationship as a higher-level entity so it can take part in another relationship.

14. Design issues and design of ER schema

Common issues: entity vs attribute, entity vs relationship, binary vs n-ary relationships, placement of attributes, and avoiding redundancy. Steps: identify entities → identify relationships and cardinalities → add attributes and keys → refine (weak entities, ISA) → draw the diagram.

15. Reduction of ER schema to tables

  • Strong entity → one table; columns = simple attributes (composite split into parts).
  • Multivalued attribute → separate table with the entity’s key + the attribute.
  • Weak entity → table with owner’s primary key + discriminator as the primary key.
  • 1:N relationship → add the “one” side’s key as foreign key on the “many” side.
  • M:N relationship → new table with both keys (+ relationship attributes).
  • ISA → one table per entity set (child holds parent’s key) or one table per child.

Diagrams & examples

Example: Student–Course (M:N) with a relationship attribute

ER:  STUDENT(roll_no, name, phone*)  --- ENROLLS(grade) ---  COURSE(course_id, title, credits)
     (phone* = multivalued attribute; ENROLLS is many-to-many)

Tables:
STUDENT(roll_no PK, name)
STUDENT_PHONE(roll_no FK, phone)          -- multivalued attribute
COURSE(course_id PK, title, credits)
ENROLLS(roll_no FK, course_id FK, grade)  -- PK = (roll_no, course_id)
CREATE TABLE Enrolls (
  roll_no   INT,
  course_id VARCHAR(10),
  grade     CHAR(2),
  PRIMARY KEY (roll_no, course_id),
  FOREIGN KEY (roll_no)   REFERENCES Student(roll_no),
  FOREIGN KEY (course_id) REFERENCES Course(course_id)
);
Exam tip: always label cardinality (1, N, M) on both sides of every diamond and underline primary keys.

Important questions

Q1. What are the advantages of DBMS over a file system?

Less redundancy and inconsistency, data sharing, integrity and security enforcement, concurrent access, backup/recovery, and data independence.

Q2. Explain the three-level architecture of a database.

Physical level (how stored), logical level (what stored and relationships) and view level (user-specific parts). It provides physical and logical data independence.

Q3. Differentiate between a weak and a strong entity set.

A strong entity set has a primary key; a weak one has only a discriminator and depends on an owner entity for identification (double rectangle in ER diagram).

Q4. Explain specialization, generalization and aggregation with examples.

Specialization splits Person into Student/Teacher; generalization merges Car and Truck into Vehicle; aggregation treats the relationship ‘Works_on’ as an entity to relate it with ‘Manager’.

Q5. How is an ER diagram converted into tables?

Each strong entity becomes a table; multivalued attributes get their own table; 1:N adds a foreign key; M:N creates a new table with both keys; weak entities include the owner’s key.

Q6. Define data dictionary and DBA.

The data dictionary stores metadata about the database; the DBA is the person/group responsible for schema definition, security, performance and recovery.

Quick revision

  • DBMS = less redundancy, more integrity, security, sharing, independence.
  • 3 levels: physical → logical → view. 2 independences: physical, logical.
  • Languages: DDL, DML, DCL, TCL.
  • Keys: super ⊃ candidate ⊃ primary; foreign key links tables.
  • Weak entity = double rectangle + discriminator + owner.
  • M:N relationship always becomes a separate table.
